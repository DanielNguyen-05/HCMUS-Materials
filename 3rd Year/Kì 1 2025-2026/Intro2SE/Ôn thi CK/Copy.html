Software Process — tổng quan

Definition

EN:
Software Process = a set of activities to develop/evolve software: Specification, Development, Validation, and Evolution.

  • Specification: define what the system should do and constraints.
  • Development: implement code + unit testing.
  • Validation: ensure the software is what the customer wants (reviews, tests).
  • Evolution: change software to meet new demands (bug fixes, features).

VI:
Software Process là tập hợp hoạt động để phát triển/tiến hoá phần mềm gồm Specification, Development, Validation, Evolution.

  • Specification: xác định hệ thống làm gì và ràng buộc.
  • Development: hiện thực mã + unit testing.
  • Validation: kiểm chứng phần mềm đúng mong muốn khách hàng (review/test).
  • Evolution: thay đổi để đáp ứng yêu cầu mới (sửa lỗi/thêm tính năng).

“What, Who, When, How?” — cách nhìn vào process

EN

  • What: deliverables/artifacts
    (e.g., Requirements Document, SAD, Source Code, Test Cases, User Manual).
  • Who: roles
    (e.g., Project Manager, Business Analyst, Designer, Developer, Tester).
  • When: schedule/phase/iteration timing.
  • How: methods, practices, tools
    (e.g., RUP, Scrum, XP, CI, SCM).

VI

  • What: sản phẩm trung gian/đầu ra
    (Requirements Document, SAD, Source Code, Test Cases, User Manual).
  • Who: vai trò
    (Project Manager, Business Analyst, Designer, Developer, Tester).
  • When: lịch, phase/iteration.
  • How: phương pháp, thực hành, công cụ
    (RUP, Scrum, XP, CI, SCM).

Software Process Model — là gì?

EN:
A Software Process Model is a simplified representation of the process from a specific perspective
(e.g., phase sequence, activities, artifacts).

VI:
Software Process Model là mô hình hoá đơn giản quy trình, nhìn từ một góc độ cụ thể
(thứ tự phase, hoạt động, artifact).

Plan-Driven vs Agile — bức tranh lớn

EN

  • Plan-driven: document-heavy, predictive, follow predefined stages
    (e.g., Waterfall, RUP in plan-driven mode).
  • Agile: iterative, incremental, people-centric, welcomes change
    (e.g., Scrum, XP).

VI

  • Plan-driven: nhiều tài liệu, dự báo trước, theo stage rõ ràng
    (Waterfall, RUP dạng truyền thống).
  • Agile: lặp–tăng trưởng, lấy con người làm trung tâm, chấp nhận thay đổi
    (Scrum, XP).

Quick comparison (so khớp nhanh)

Dimension Plan-driven Agile
Requirements Prefer stable upfront Expect changing
Planning Big upfront planning Iterative planning (per Sprint)
Documentation Extensive Just-enough
Risk handling Predict/mitigate early Surface early via short iterations
Team Larger, specialized roles Smaller, cross-functional
Delivery One major release Frequent increments

Waterfall Model — truyền thống

EN:
Waterfall is sequential/linear: complete one stage before the next; no overlap/backtracking.
Best when requirements are stable.

Typical stages & outputs

  • Requirements Definition → Requirements Document
  • Design & Analysis → Software Architecture Document (SAD)
  • Implementation & Unit Testing → Source Code, Unit Test Cases
  • Integration, System Testing & Deployment → Test Results, Release
  • Operation & Maintenance → User Manual, Training Docs

Problems:
inflexible partitioning, hard to handle change, suited to some large systems engineering.

Use when:
domain is well-understood, stable requirements, compliance/regulatory contexts.

VI:
Waterfall là tuần tự/tuyến tính: xong stage trước mới sang stage sau, không chồng lấn/quay lại.
Phù hợp khi yêu cầu ổn định.

  • Stage & output điển hình: Requirements Document, SAD, Source Code, Test Results, User Manual.
  • Vấn đề: chia stage cứng, khó xử lý thay đổi, thường dùng cho large systems engineering.
  • Khi dùng: yêu cầu rõ ràng, ổn định, cần tuân thủ.

Tip:
Phân biệt Validation (“xây đúng cái khách hàng cần?”) vs Verification (“xây đúng theo đặc tả không?”).
Waterfall hay nhấn mạnh Verification theo từng stage; Agile nhấn mạnh Validation liên tục với người dùng.

RUP (Rational Unified Process) — có cấu trúc nhưng lặp

EN

RUP is iterative and described from three perspectives:

  • Dynamic perspective: time-based phases.
  • Static perspective: activities/workflows.
  • Practical perspective: best practices.

Iterations = mini-waterfalls with entry/exit criteria.

Four phases (each has one or more iterations)

Mô tả Activity Dynamic (Phases) Static (Workflows) Practical (Best practices)
Xác định phạm vi, mục tiêu, business case Inception Business Modeling, Requirements Develop iteratively, Manage requirements
Chuẩn bị công cụ, môi trường phát triển Inception → Elaboration Environment Provide tool support, Standardize process
Phân tích domain, giải quyết risk, thiết kế kiến trúc lõi Elaboration Requirements, Analysis & Design, SCM, PM Architecture-centric, Risk-driven
Thiết kế chi tiết, coding, unit test, tích hợp Construction A&D, Implementation, Testing, SCM Component-based, Continuous verification
Kiểm thử hệ thống, acceptance test Construction → Transition Testing, Deployment Verify quality continuously
Triển khai, training, hỗ trợ khách hàng Transition Deployment, PM Manage user involvement
Quản lý thay đổi, version control Xuyên suốt SCM Control changes
Quản lý dự án Xuyên suốt Project Management Track progress, Risk management

Roles: Project Manager, Business Analyst, Designer/Architect, Developer, Tester.

Strengths: clear artifacts, roles, risk-driven architecture, scalable.
Weaknesses: document-heavy if over-formalized.
Use when: medium-to-large systems, architecture-first, partial agility.

VI

RUP là iterative, có 3 góc nhìn: Dynamic, Static, Practical.
4 phase: Inception, Elaboration, Construction, Transition.
Workflow: Business Modeling, Requirements, Analysis & Design, Implementation, Testing, Deployment, SCM, PM.
Mạnh: rõ artifact/role, kiến trúc dẫn dắt rủi ro.
Yếu: dễ quá tải tài liệu nếu áp dụng cứng.

Agile — giá trị & bối cảnh dùng

EN

Agile favors:

  • Individuals & Interactions
  • Working Software
  • Customer Collaboration
  • Responding to Change

Best for small teams (2–20), short iterations (1–2 weeks), non-safety-critical products.

Strengths: fast feedback, adaptability.
Weaknesses: less suitable for safety-critical or very large systems.

VI

Agile đề cao Individuals & Interactions, Working Software, Customer Collaboration, Responding to Change.
Phù hợp đội nhỏ, iteration ngắn, không safety-critical.

Scrum — khung làm việc Agile phổ biến

EN

  • Artifacts: Product Backlog, Sprint Backlog, Increment, Burndown, DoD.
  • Roles: Scrum Master, Product Owner, Developers/Team.
  • Events: Sprint Planning, Daily Scrum, Sprint Review, Retrospective.
  • Cadence: Sprint 1–2 weeks (up to 4).

VI

Scrum dùng Sprint theo time-box, backlog và role rõ ràng.
Artifact: Product Backlog, Sprint Backlog, Increment, Burndown, DoD.
Role: Scrum Master, Product Owner, Developers.
Sự kiện: Planning, Daily, Review, Retro.

Extreme Programming (XP) — đẩy “thực hành tốt” đến cực hạn

Overview

EN:
XP pushes good practices to extremes to maximize feedback and quality.

VI:
XP đẩy các thực hành tốt lên mức cực đại để tối đa phản hồi (feedback) và chất lượng (quality).

Core Practices (12 Practices)

# Practice Explanation (EN) Giải thích (VI)
1 The Planning Game Decision-making is given to the person/team member with the best knowledge. Requirements and priorities are decided collaboratively between customer and developers. Quyết định được giao cho người có kiến thức tốt nhất. Khách hàng và dev cùng quyết định và ưu tiên yêu cầu.
2 Small Releases Deliver working software in small, frequent releases to get quick feedback and easier progress tracking. Phát hành phần mềm nhỏ, thường xuyên → phản hồi nhanh, dễ theo dõi tiến độ, dễ quản lý.
3 Metaphor Use a shared story or analogy to describe how the system works so everyone shares the same vision. Dùng ẩn dụ/câu chuyện chung để mô tả hệ thống, giúp cả team hiểu giống nhau.
4 Simple Design Always choose the simplest design that works. Avoid over-engineering. Thiết kế đơn giản nhất có thể nhưng vẫn chạy được → tránh phức tạp hoá.
5 Testing (TDD) Adopt Test-Driven Development: write tests before code. Continuous testing ensures quality. Dùng TDD: viết test trước khi code. Kiểm thử liên tục để đảm bảo chất lượng.
6 Refactoring Continuously improve code structure without changing functionality. Liên tục tái cấu trúc code để dễ đọc, dễ bảo trì, không đổi chức năng.
7 Pair Programming Two developers work at one workstation: one codes, one reviews in real time. Hai dev làm chung một máy: một người code, một người review ngay lập tức.
8 Collective Ownership Any developer can change any part of the codebase. No single owner per module. Bất kỳ dev nào cũng có thể sửa bất kỳ phần code nào, không có “chủ sở hữu” riêng lẻ.
9 Continuous Integration Integrate code into the main branch multiple times a day; automated tests run each time. Tích hợp code nhiều lần mỗi ngày, chạy test tự động để phát hiện lỗi sớm.
10 40-hour Week Maintain a sustainable pace (~40 hours/week). Avoid overtime to prevent burnout. Giữ nhịp độ bền vững (~40h/tuần), tránh OT để không kiệt sức.
11 On-site Customer A real customer representative is available daily to clarify requirements. Có khách hàng (hoặc đại diện) tham gia thường xuyên để làm rõ yêu cầu.
12 Coding Standards All developers follow the same coding standards to improve readability and maintainability. Tuân thủ chuẩn coding chung → code dễ đọc, dễ bảo trì, tránh hiểu nhầm.

Summary (VI)

XP đẩy thực hành tốt lên mức cực đại để tăng phản hồi và chất lượng:
Planning Game, Small Releases, Metaphor, Simple Design, Testing (TDD), Refactoring, Pair Programming, Collective Ownership, Continuous Integration, 40-hour Week, On-site Customer, Coding Standards.

Thuật ngữ then chốt dễ nhầm (Quick Clarifiers)

EN

  • Iteration vs Increment
    • Iteration: a time-box of work
    • Increment: a usable product produced after an iteration
  • Unit / Integration / System Testing
    • Unit: functions/classes
    • Integration: interactions between components
    • System: end-to-end behavior
  • SCM (Configuration & Change Management)
    Track versions, branches, changes, approvals.
  • Definition of Ready (DoR) vs Definition of Done (DoD)
    • DoR: ready to start
    • DoD: meets completion quality criteria

VI

  • Iteration vs Increment
    • Iteration: hộp thời gian làm việc
    • Increment: sản phẩm dùng được sau iteration
  • Unit / Integration / System Testing
    • Unit: hàm/lớp
    • Integration: tương tác giữa module
    • System: kiểm thử đầu–cuối
  • SCM
    Quản lý phiên bản, nhánh, thay đổi.
  • DoR vs DoD
    • DoR: điều kiện để bắt đầu
    • DoD: điều kiện để hoàn tất

Khi nào chọn mô hình nào? (Decision Hints)

EN

  • Choose Waterfall if requirements are stable, the domain is well-regulated, and sequential gate reviews are required.
  • Choose RUP if you need architecture-first, clear artifacts/roles, and iterations for medium–large projects.
  • Choose Scrum / XP if you need fast feedback, changing requirements, small teams, and frequent increments.

VI

  • Chọn Waterfall khi yêu cầu ổn định, lĩnh vực quy chuẩn cao, cần cổng duyệt tuần tự.
  • Chọn RUP khi cần architecture-first, artifact/role rõ ràng, iteration cho dự án vừa/lớn.
  • Chọn Scrum / XP khi cần phản hồi nhanh, yêu cầu hay thay đổi, team nhỏ, increment thường xuyên.

Software Project Management — Tổng quan

Overview

EN:
The goal of Software Project Management is to ensure the project delivers on time, within budget, meets requirements, has high quality, and achieves customer satisfaction.

VI:
Software Project Management có mục tiêu: đảm bảo dự án được phát triển và bàn giao đúng hạn, trong ngân sách, đáp ứng yêu cầu, chất lượng cao, và khách hàng hài lòng.

Roles — Các vai trò chính

Project Manager (PM)

EN:
The PM leads the team to achieve project objectives. A single important person who plays multiple roles: planner, coordinator, communicator, risk handler, motivator.

VI:
PM là người dẫn dắt team để đạt mục tiêu dự án. Đây là vai trò quan trọng nhất, kiêm nhiều trách nhiệm: planner, coordinator, communicator, quản lý rủi ro, thúc đẩy động lực.

Technical Architect (TA)

EN:
TA ensures technical soundness of the solution, defines architecture, sets coding standards, evaluates technology.

VI:
TA đảm bảo tính kỹ thuật của giải pháp, thiết kế architecture, đặt coding standards, đánh giá và lựa chọn công nghệ phù hợp.

Business Analyst (BA)

EN:
BA gathers requirements, communicates with stakeholders, ensures business needs are understood by the technical team.

VI:
BA phân tích và ghi nhận requirements, trao đổi với khách hàng/stakeholder, giúp team kỹ thuật hiểu đúng nhu cầu nghiệp vụ.

Tester

EN:
Tester validates functionality, ensures quality, reports defects, verifies fixes.

VI:
Tester kiểm thử chức năng, đảm bảo chất lượng, báo lỗi, xác nhận lỗi đã được sửa.

Maintainer

EN:
Maintainer supports the software post-deployment, fixes bugs, applies patches, manages upgrades.

VI:
Maintainer duy trì phần mềm sau khi bàn giao, sửa lỗi, cập nhật bản vá, quản lý phiên bản nâng cấp.

Create team cohesion, assign roles, encourage collaboration.

Xây dựng tinh thần đội nhóm, phân vai, khuyến khích hợp tác.

6. Project Monitoring, Controlling & Reviews

EN:
Monitor progress via reports, detect deviations, solve problems. Conduct reviews for quality and alignment.

Giám sát tiến độ qua report, phát hiện sai lệch, giải quyết vấn đề. Tổ chức review để đảm bảo chất lượng và tiến độ.

EN:
Maintain good communication, manage expectations, gather feedback.

Giữ quan hệ với customer/user, quản lý kỳ vọng, thu thập phản hồi.

Software Requirements — Yêu cầu phần mềm

Requirement Type Explanation (EN) Giải thích (VI)
User requirements High-level system services, described in natural language + diagrams. Audience: end-users/customers. Mô tả mức cao bằng ngôn ngữ tự nhiên/sơ đồ. Đối tượng: người dùng, khách hàng.
System requirements Detailed system functions, constraints, interfaces. Audience: devs, testers, maintainers. Mô tả chi tiết chức năng, ràng buộc, interface. Đối tượng: dev, tester, maintainer.
Functional requirements Define what the system should do (inputs, outputs, behaviors). Hệ thống phải làm gì (input, output, xử lý).
Non-functional requirements Define quality attributes: performance, security, usability, reliability, etc. Thuộc tính chất lượng: hiệu năng, bảo mật, usability, độ tin cậy, …
Domain requirements Constraints from the application domain (rules, standards, regulations). Yêu cầu/ràng buộc từ miền ứng dụng (chuẩn, luật, quy định).

Software Analysis and Design

1. Software Architecture

Khái niệm Giải thích (EN) Giải thích (VI)
Why detail / form an architecture? - Stakeholder communication: Architecture is a shared reference to discuss system structure.
- System analysis: Helps check if non-functional requirements (performance, security, scalability) are achievable, and foresee future extensions.
- Large-scale reuse: Architectural patterns/components may be reused across different systems.		 - Stakeholder communication: Architecture là “tài liệu tham chiếu” chung để stakeholder thảo luận.
- System analysis: Giúp phân tích xem hệ thống có đáp ứng non-functional requirements không, và chuẩn bị cho future extension.
- Large-scale reuse: Có thể tái sử dụng kiến trúc (pattern/component) cho nhiều hệ thống.
Scalability - Vertical Scaling (scale up): Increase resources of a single node (faster CPU, more RAM).
- Horizontal Scaling (scale out): Add more nodes/servers to distribute load.		 - Vertical scale (scale up): Nâng cấp phần cứng 1 máy (CPU, RAM).
- Horizontal scale (scale out): Thêm nhiều máy/nodes để chia tải.
Architectural Critical Requirements Non-functional requirements that drive the architecture: performance, scalability, security, availability, maintainability, reliability. Các non-functional requirements quan trọng quyết định kiến trúc: hiệu năng, khả năng mở rộng, bảo mật, khả năng sẵn sàng, bảo trì, độ tin cậy.

2. Architectural Design

Khái niệm Giải thích (EN) Giải thích (VI)
Based on Requirements Architecture must be derived from requirements (functional + non-functional). Kiến trúc phải hình thành dựa trên requirements (functional + non-functional).
Impact on Performance - Localize critical operations (run close to where data resides).
- Minimize inter-component communication.
- Prefer coarse-grained components over fine-grained ones to reduce overhead.		 - Gom critical operations lại gần dữ liệu.
- Giảm tối đa giao tiếp giữa components.
- Dùng coarse-grained component thay vì quá chi tiết để giảm overhead.
Loosely coupled vs. Tightly coupled - Loosely coupled: Components have minimal dependencies, easier to change or replace.
- Tightly coupled: Strong interdependencies, harder to modify, less flexible.		 - Loosely coupled: Các component phụ thuộc ít → dễ thay đổi/nâng cấp.
- Tightly coupled: Phụ thuộc chặt → khó thay đổi, kém linh hoạt.
Fine-grained vs. Coarse-grained components - Fine-grained: Small components, detailed functions; flexible but high communication overhead.
- Coarse-grained: Larger modules, handle more functionality; less flexible but better performance.		 - Fine-grained: Thành phần nhỏ, chi tiết, linh hoạt nhưng tốn overhead giao tiếp.
- Coarse-grained: Thành phần lớn, gói nhiều chức năng, ít overhead hơn → performance cao hơn.

3. Detailed Design (Low-level Design)

Khái niệm Giải thích (EN) Giải thích (VI)
High-level vs. Detailed design - High-level design (architecture): defines system structure, main components, data flow.
- Detailed design (low-level): defines class structures, methods, algorithms, interactions.		 - High-level design: Kiến trúc tổng thể, component chính, data flow.
- Detailed design: Chi tiết lớp, method, thuật toán, tương tác.
Class Diagram Shows system’s classes, attributes, methods, relationships (association, inheritance, aggregation, composition). Biểu diễn các class, thuộc tính, method, quan hệ (association, inheritance, aggregation, composition).
Sequence Diagram Shows dynamic behavior: object interactions, message passing, order of operations. Biểu diễn hành vi động: đối tượng tương tác thế nào, gửi/nhận message, thứ tự thực thi.

📌 Tóm nhanh để nhớ

  • Architecture: hỗ trợ stakeholder communication, system analysis, reuse.
  • Scalability: Horizontal vs Vertical.
  • Performance: localize operations, minimize communication, prefer coarse-grained.
  • Design: Loosely vs tightly coupled; fine-grained vs coarse-grained.
  • Detailed design:
    • Class Diagram → cấu trúc tĩnh
    • Sequence Diagram → tương tác động

Software Verification vs. Validation

1. Definitions

Concept Explanation (EN) Giải thích (VI)
Verification “Are we building the product right?” → Ensure the software conforms to specifications. “Chúng ta có xây đúng theo đặc tả không?” → Đảm bảo phần mềm tuân thủ specification.
Validation “Are we building the right product?” → Ensure the software meets user needs and is usable. “Chúng ta có xây đúng cái người dùng cần không?” → Đảm bảo phần mềm đúng nhu cầu, hữu ích, dễ dùng.

2. Why do we need both Verification & Validation?

Reason EN Explanation VI Explanation
Discovery of defects Both verification and validation help find defects early. Giúp phát hiện lỗi trong phần mềm sớm.
Usefulness & usability Validation ensures the software is useful and usable. Validation kiểm tra phần mềm có hữu ích và dễ dùng không.
Confidence Combined V&V builds confidence in the quality of software. Kết hợp V&V giúp tạo niềm tin vào chất lượng phần mềm.

3. Techniques for Verification & Validation (V&V)

3.1 Static Inspection

Technique Description (EN) Mô tả (VI)
Static inspection Analyze artifacts/work products without executing the program. Phân tích artifact (tài liệu, code) mà không chạy chương trình.
Review Peer reviews, walkthroughs, inspections. Đọc chéo, walkthrough, inspection.
Static analysis tools Check code quality, style, and potential bugs. Phát hiện bug tiềm năng, code smell, vấn đề style.

3.2 Dynamic Inspection

Technique Description (EN) Mô tả (VI)
Dynamic inspection Run the software and analyze its behavior. Chạy phần mềm và phân tích hành vi.
Testing Unit test, integration test, system test. Kiểm thử unit, integration, system.
Dynamic analysis tools Runtime monitoring (memory leak, performance). Theo dõi runtime (rò rỉ bộ nhớ, hiệu năng).

3.3 Development Approaches Supporting V&V

Approach Explanation (EN) Giải thích (VI)
Test-Driven Development (TDD) Write tests before code. Code is written only to make tests pass, ensuring requirements are met. Viết test trước code. Code chỉ được viết để pass test, đảm bảo đúng yêu cầu.
Model-Driven Development (MDD) Create models (e.g., UML diagrams) and automatically generate code/tests from models. Tạo model (ví dụ UML), rồi sinh code/test từ model.

📌 Quick Summary (Tóm nhanh để nhớ)

  • Verification = đúng theo đặc tả
  • Validation = đúng cái người dùng cần
  • Cần cả hai để phần mềm vừa đúng vừa dùng được

Techniques:

  • Static: review, static analysis
  • Dynamic: testing, runtime analysis
  • TDD: test trước, code sau
  • MDD: model → code/test
